Automated review generated by [PromptPCB](https://github.com/gatordevin/promptpcb) using real datasheet extraction and LLM analysis.

**Model:** claude-opus-4.8 | **Cost:** $0.28 | **Components:** 45 | **Datasheets:** 6

## Summary

This is an RP2040-based USB-C powered microcontroller board with battery management. Power architecture: USB-C VBUS feeds a BQ24075 (U4) Li-Ion charger/power-path manager producing VSYS, which feeds an MCP1700-3.3 LDO (U2) producing +3V3. The RP2040 (U1) runs its internal core LDO (VREG_VOUT=+1V1) for DVDD. A W25Q16 QSPI flash (U3) provides boot storage, a 12MHz crystal (Y1) provides the reference clock, and a MAX17048 (U5) fuel gauge monitors the battery over I2C. GPIO are broken out on 20-pin headers J2/J3 and SWD on J4. Key risk areas: a serious power-domain/abs-max violation where the LDO output (U2.VOUT) is wired to +3V3 but the LDO INPUT (VSYS) is on a separate rail that can exceed VOUT, plus the BQ24075 OUT being tied to VSYS while BAT-derived VSYS feeds the +3V3 LDO whose input can sag below output; missing fuel gauge connection topology issues; QSPI flash boot mode considerations; missing TVS on USB; and crystal load cap value mismatch potential. Several abs-max and floating-pin checks pass, but multiple required-component and protocol issues were found.

### Errors

#### 🔴 Fuel gauge VDD connected to BAT+ but I2C pull-ups reference +3V3 — domain mismatch and missing dedicated pull-ups
**Components:** U5, R12, R13

**Issue:** The MAX17048 (U5) VDD is powered from BAT+ (a 3.0–4.2V Li-Ion rail) but its I2C lines SDA/SCL are pulled up to +3V3 via R12/R13. The MAX17048 datasheet REQUIRES R_PU_SDA and R_PU_SCL to VDD (i.e., BAT+), not to a separate logic rail. When BAT+ < 3.3V (discharged battery), the +3V3 pull-ups will back-drive current into the MAX17048 I/O pins relative to its lower VDD, and when BAT+ > 3.3V the RP2040 (IOVDD=3.3V) Vih may not be met cleanly. This is a level-domain mismatch between a 3.3V host and a battery-referenced slave.

**Evidence:**
```
Net BAT+: U5.3:VDD_3. Net GPIO4: R12.2, U5.8:SDA_8 with R12.1 on +3V3. Net GPIO5: R13.2, U5.7:SCL_7 with R13.1 on +3V3. Datasheet REQUIRED: R_PU_SDA=10kΩ→SDA,VDD and R_PU_SCL=10kΩ→SCL,VDD.
```

**Fix:** Either power U5 VDD from +3V3 (the MAX17048 VDD doubles as the cell-sense input, so this changes the measured voltage — verify intended sensing) or, if VDD must be BAT+, ensure pull-up rail compatibility. Best practice for a battery fuel gauge is to keep VDD on the cell and use a level-tolerant I2C interface; confirm RP2040 inputs tolerate BAT+-referenced highs and that pull-ups do not back-drive when BAT+ < 3.3V.

#### 🔴 QSPI_SS pull-up to +3V3 plus a series/parallel resistor network — verify BOOTSEL implementation
**Components:** R6, R7, SW1, U1, U3

**Issue:** QSPI_SS net ties U1.56 (QSPI_SSn), U3.1 (/CS), R6.2, and R7.1 together. R7 (10K) pulls QSPI_SS to +3V3. SW1 connects to R6.1 (Net-(R6-Pad1)) and R6.2 is on QSPI_SS, while SW1.1 is GND. **Evidence:**

**Fix:** Confirm this matches the RP2040 hardware design guide BOOTSEL topology (R7 pull-up to 3V3, R6 series to button, button to GND). Topology appears correct; verify values against reference design (typically R7=10K to flash CS, button via resistor to QSPI_SS).

#### 🔴 Missing TVS/ESD protection on USB-C VBUS and data lines
**Components:** J1, VBUS

**Issue:** The USB-C connector J1 exposes VBUS and the USB D+/D- data lines to the outside world with no TVS diodes for ESD/surge protection. VBUS (up to 5V, externally exposed, high-energy) feeds directly into U4.IN. USB data lines connect via R3/R4 to the RP2040 USB pins. No ESD protection devices are present in the netlist.

**Evidence:**
```
VBUS net connects J1.A4/A9/B4/B9 directly to U4.13:IN and U4.5:EN2 with only bulk cap C13(10uF). USB_D+/USB_D- connect J1.A6/B6/A7/B7 through R3/R4 (27Ω) to U1.46/47 with no TVS.
```

**Fix:** Add a TVS array (e.g., USBLC6-2 or equivalent) on D+/D- near the connector and a unidirectional TVS on VBUS rated above 5V working voltage.

#### 🔴 BQ24075 EN2 tied to VBUS sets SUSPEND/PROG behavior incorrectly with EN1 grounded
**Components:** U4

**Issue:** U4 EN1 (pin 6) is tied to GND and EN2 (pin 5) is tied to VBUS (logic high when USB present). Per the datasheet mode table: EN2=1, EN1=0 → PROG mode (IINmax = KILIM/RILIM). That is a valid intentional choice IF R_ILIM is populated. R11 (3.1K) is on ILIM, giving IINmax = 1550/3100 ≈ 0.5A. This is consistent with PROG mode. However, tying EN2 directly to VBUS means EN2 follows the full VBUS voltage — confirm EN2 abs-max tolerates VBUS (5V) and that this is the intended fixed-PROG-mode configuration rather than dynamic USB100/USB500 negotiation.

**Evidence:**
```
GND: U4.6:EN1_6. VBUS: U4.5:EN2_5. Net-(U4-ILIM): R11.1, U4.12 with R11=3.1K → IINmax≈500mA. CE (pin4) tied to GND (enabled, correct).
```

**Fix:** Confirm PROG mode at 500mA is intended. EN2 logic high threshold Vih=1.4V is satisfied by VBUS. Acceptable if PROG mode @500mA is the design intent; otherwise drive EN1/EN2 from GPIO for dynamic current selection.

#### 🟡 BQ24075 input cap exceeds USB-IF inrush limit guidance check / value OK but verify
**Components:** U4, C13

**Issue:** The BQ24075 datasheet states C_IN must be <10µF for USB-IF inrush compliance. The VBUS net has C13=10µF. This is at the boundary (10µF, not less than 10µF) and is the bulk cap on the USB input feeding U4.IN. Combined with C13 being the only IN-side decoupling, this is exactly at the limit and may marginally violate USB-IF inrush.

**Evidence:**
```
VBUS: C13.1 (10uF), U4.13:IN_13. Datasheet C_IN = 1µF to 10µF, 'Must be <10µF for USB-IF inrush compliance'.
```

**Fix:** Reduce C_IN to ≤4.7µF (e.g., 4.7µF) to stay safely under the 10µF USB-IF inrush ceiling, or add inrush limiting.

#### 🟡 ADC input GPIO26-29 lack RC filtering
**Components:** U1, J3

**Issue:** GPIO26/ADC0 through GPIO29/ADC3 are routed directly to header J3 with no series resistor or filter capacitor. For ADC use these analog inputs should have RC anti-alias/filtering. Also the datasheet warns ADC inputs must not exceed IOVDD (3.3V) to prevent ESD diode leakage — external header pins offer no clamping.

**Evidence:**
```
GPIO26{slash}ADC0: J3.7, U1.38. GPIO27/ADC1: J3.6, U1.39. GPIO28/ADC2: J3.4, U1.40. GPIO29/ADC3: J3.2, U1.41. No series R or cap on these nets.
```

**Fix:** Add series resistor + small cap (e.g., 1k + 100pF) on ADC channels actually used as analog inputs, and ensure external sources cannot drive above IOVDD.

#### 🟡 Crystal load capacitor value cannot be verified against crystal spec
**Components:** Y1, C15, C16, R5

**Issue:** The 12MHz crystal Y1 uses 33pF load caps (C15, C16) and a series feedback resistor R5=1K on XOUT. The crystal datasheet was unavailable, so the required load capacitance (CL) cannot be confirmed. 33pF caps imply a crystal CL ≈ (33/2) minus stray ≈ ~15pF+stray. The RP2040 reference design typically uses 15pF or 27pF caps with a 1K series resistor depending on the crystal. 33pF may over-load a typical 12MHz crystal designed for lower CL.

**Evidence:**
```
XIN: C15.2(33pF), U1.20, Y1.3. XOUT: R5.2, U1.21. Net-(C16-Pad2): C16.2(33pF), R5.1, Y1.1. R5=1K series.
```

**Fix:** Obtain crystal CL spec and compute Cload = 2*(CL - Cstray). Confirm 33pF matches; for many 12MHz crystals (CL=18pF) the caps should be ~27-30pF less stray — verify, and confirm R5 series resistor value matches the RP2040 design guide (typically 1kΩ).

#### 🔵 RUN pin broken out to header with no external pull-up or debounce
**Components:** U1, J3

**Issue:** RUN (pin 26) is routed to J3.11 only. The RP2040 has an internal pull-up so floating is acceptable, but exposing RUN on a header without a small cap (typically 1µF) for noise immunity / clean reset can cause spurious resets in noisy environments. The reference design recommends a ~1µF cap on RUN.

**Evidence:**
```
RUN: J3.11:Pin_11_11, U1.26:RUN_26. No cap or pull-up on this net.
```

**Fix:** Add a 1µF cap from RUN to GND (and optional external pull-up) per the RP2040 hardware design guide for reliable reset behavior.
